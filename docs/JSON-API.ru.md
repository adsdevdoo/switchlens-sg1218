# Справочник `/stats.json` — схема 1

Актуально для **SwitchLens v0.1.1-experimental-uart**, 17 октября 2026 года.
Статус: **рабочая прошивка с проверенными загрузкой, UART и JSON**.
Модель: TP-Link TL-SG1218MPE(UN) V5.0. На экземпляре владельца подтверждены
загрузка, UART `help` и два полных ответа JSON с изменяющимися счётчиками.
[Результаты и оригинальные материалы](evidence/2026-10-17-switchlens/README.ru.md).

Этот справочник описывает фактическую реализацию. Формальная структура:
[JSON Schema 2020-12](../schema/stats.schema.json). Источники значений:
[адаптер](../target/adapter.c), [MIB reader](../src/sg_mib.c),
[сериализатор](../src/sg_stats.c), [карта доказательств](../research/metric-sources.json).
Исторический проект контракта находится в `research/JSON-CONTRACT.txt`;
он не заменяет актуальную схему и этот документ.

## Статус статистики вентиляторов

В v0.1.1 нет полей RPM, исправности вентиляторов, режима охлаждения или
температуры. [Исследование GPIO/PoE](../research/COOLING.ru.md) и отдельный
диагностический JSON устанавливают источники сырых сигналов; физическая связь
с вентиляторами ещё не подтверждена. `diagnostic_version` декодера независим
от `schema_version` API. Его `fan_status: null` и `fan_rpm: null` не означают
добавления полей в установленный endpoint.

## Получение ответа

Используется штатная форма входа, cookie `H_P_SSID` и тот же IP для входа и сбора.
Это не Basic Auth и не Bearer. Исключение v0.1.3 для открытого JSON не сработало
на устройстве; v0.1.4 удаляет его и возвращает штатные байты авторизации.
[Последовательность входа, curl и описание исправления](HTTP-AUTH.ru.md).

В браузере войти в штатную панель и затем открыть `/stats.json`. Автоклиент
отправляет POST на `/logon.cgi`, сохраняет cookie и читает `/stats.json` с ней
с той же машины. При HTML входа/истечении сессии повторяет авторизацию.
HTML — ошибка даже при HTTP 200. Заголовок v0.1.4: `X-SwitchLens-Build: v0.1.4`.
Endpoint только читает. Полный автоматический сетевой вход на устройстве владельца
ещё не проверен; поля запроса взяты из встроенной формы.

## Типы, отсутствие данных и целостность

| Значение | Значение для потребителя |
| --- | --- |
| `null` | Показание недоступно, источник/семантика не установлены, чтение не удалось либо поле неприменимо. Причина зависит от поля |
| `0`, `0.0`, `"0"` | Получен ноль соответствующего числового типа; это не замена `null` |
| `false` | Получен отрицательный логический признак, например link down |
| `"528836"` | Строка десятичного целого счётчика, не JSON number |

Все предусмотренные схемой ключи присутствуют; неизвестные значения сохраняются
как `null`. Счётчики — строки без знака и ведущих нулей, кроме самого `"0"`.
Допустимый максимум — `18446744073709551615` (`uint64`). Регулярное выражение
схемы ограничивает длину, но клиент должен отдельно проверить этот максимум.
В JavaScript использовать `BigInt`, в Python — `int`; преобразование больших
счётчиков в JavaScript `Number` может потерять точность.

JSON формируется последовательно, а не как атомарный снимок всех регистров.
Сумма отдельно прочитанных категорий может немного отличаться от отдельно
прочитанного агрегата. PoE берётся из штатного RAM-кэша; время его обновления
не известно. Поддержка поля схемой не доказывает точность показания на железе.

При ошибке транспорта возможен оборванный JSON. Клиент принимает только целый
документ ожидаемой схемы; частично прочитанные значения не следует публиковать.
Дедлайн обработчика задан в raw ticks, а не в подтверждённых секундах.

## Верхний уровень

| Поле | Тип | Описание |
| --- | --- | --- |
| `schema_version` | integer, всегда `1` | Версия структуры JSON, не версия прошивки |
| `system` | object | Сведения об устройстве и его сетевой конфигурации |
| `poe` | object | Общие показатели PoE |
| `ports` | array, ровно 18 элементов | Порты в порядке 1–18 |
| `loop_prevention` | object | Сырые программные маски обнаружения петель |

## `system`

Во всех строках таблиц ниже `?` у типа означает, что разрешён `null`.

| Поле | Тип | Описание, источник и ограничения |
| --- | --- | --- |
| `model` | string? | Константа адаптера `TL-SG1218MPE`; это не универсальное автоопределение модели |
| `hardware_version` | string? | Полная строка аппаратной версии, например `TL-SG1218MPE 5.0` |
| `firmware_version` | string? | Полная штатная строка сборки, до 64 исходных байт. В нашем выпуске сохранено `1.0.0 Build 20230616 Rel.57668` |
| `name` | string? | Совместимый псевдоним `description`, не отдельное имя хоста |
| `description` | string? | Изменяемое Device Description, до 32 исходных байт; строки экранируются для JSON |
| `mac` | string? | MAC коммутатора, полученный через регистры ASIC, в формате `xx:xx:xx:xx:xx:xx` |
| `uptime_seconds` | number? | Сейчас всегда `null`: коэффициент перевода в секунды не подтверждён |
| `uptime_ticks_raw` | integer? | 32-битное значение из RAM `0xbf002e90`, диапазон 0–4294967295. Может оборачиваться; единица времени не установлена |
| `ip_address` | string? | Текущий IPv4 управления из RAM |
| `subnet_mask` | string? | Маска IPv4 |
| `default_gateway` | string? | IPv4 шлюза |

Исходная строка `firmware_version` после обновления не означает откат.
Установленный вариант определяется материалами прошивки, поведением и, при
необходимости, чтением образа; сама эта строка не идентифицирует SwitchLens.

## Общий объект `poe`

| Поле | Тип / единица | Описание |
| --- | --- | --- |
| `budget_w` | number?, Вт | Настроенный системный лимит мощности из кэша; raw / 10 |
| `consumption_w` | number?, Вт | Системное потребление из кэша; raw / 10. JSON не обрезает его сверху до бюджета |
| `remaining_w` | number?, Вт | `max(budget_w - consumption_w, 0)`; расчётное значение |
| `consumption_raw` | integer? | Исходное неотрицательное значение потребления до деления на 10 |
| `recovery_enabled` | boolean? | Общий флаг штатного PoE Auto Recovery; неподдержанный код даёт `null` |

На стенде получено 250 Вт бюджета, 0 Вт потребления и 250 Вт остатка.
Это наблюдение при отсутствии выдаваемого PoE по отчёту устройства, а не
измерение точности под нагрузкой и не доказательство максимальной мощности БП.

## `ports[]`: связь и конфигурация

| Поле | Тип | Описание |
| --- | --- | --- |
| `port` | integer 1–18 | Номер порта в JSON; порядок массива фиксирован |
| `admin_enabled` | boolean? | Административное разрешение порта, не признак наличия соединения |
| `link_up` | boolean? | Прочитанный текущий статус соединения |
| `speed_config_code` | integer? | Код настроенного режима, вычисленный по штатным конфигурационным битам. Сохраняется как код; это не скорость в Мбит/с |
| `speed_actual_code` | integer? | Код фактического состояния по таблице ниже |
| `speed_mbps` | 10, 100, 1000 или null | Текущая скорость в Мбит/с; `null` при отсутствии линка/ошибке/неизвестном коде |
| `duplex` | `half`, `full` или null | Полудуплекс/полный дуплекс; `null` при отсутствии линка или ошибке чтения |
| `flow_control_configured` | boolean? | Настройка управления потоком |
| `flow_control_active` | boolean? | Линк поднят и одновременно установлены RX/TX flow-control биты; не число pause-кадров |
| `lag_id` | integer? | Сейчас `null`: привязка к группе агрегации не реализована |
| `counters` | object | 49 полей счётчиков, описаны ниже |
| `poe` | object или null | Для портов 1–16 объект PoE; для 17–18 — `null` |

Код использует mapping: порты JSON 1–16 → ASIC 0–15, 17 → 24, 18 → 25.
Это установленное поведение адаптера; независимая проверка каждого разъёма
на лицевой панели ещё не выполнена. Строки загрузки `set port 24…27` не являются
самостоятельным доказательством нумерации панели.

| `speed_actual_code` | Интерпретация текущим адаптером |
| --- | --- |
| 0 | Линк отсутствует |
| 1 | Другая/необычная комбинация speed/duplex, не перечисленная ниже |
| 2 | 10 Мбит/с, half |
| 3 | 10 Мбит/с, full |
| 4 | 100 Мбит/с, half |
| 5 | 100 Мбит/с, full |
| 6 | 1000 Мбит/с, full |
| null | Статус прочитать не удалось |

Эту таблицу нельзя применять к `speed_config_code`: это разные кодировки.
На стенде для порта 1 получены config=5, actual=6, speed=1000, duplex=full.
Сопоставление всех настроенных режимов с панелью ещё предстоит.

## `ports[].counters`

Все значения — десятичные строки или `null`, RX/TX указаны **со стороны свитча**.
Это накопленные счётчики, а не байты/пакеты в секунду. Операций сброса в endpoint нет.

Столбец selector обозначает исследованный путь штатного MIB getter. Адаптер
использует собственный reader с проверкой ошибок, а не вызывает проблемный getter.
Для отдельных регистров прочитывается 32-битное слово; для byte counters — два слова
с повтором high–low–high до трёх попыток. Это способ чтения, а не доказательство
полной аппаратной разрядности и отсутствия побочных эффектов на всех режимах ASIC.

### Трафик и агрегаты

| Поле | Значение | Selector / построение |
| --- | --- | --- |
| `rx_bytes` | Принятые байты | 1, два слова; учитывать ли FCS/служебные байты, стендом не установлено |
| `tx_bytes` | Переданные байты | 9, два слова; точный состав байт также требует сверки |
| `rx_good_packets` | Штатный агрегат принятых пакетов | RX unicast + multicast + broadcast, собственная 64-битная сумма |
| `tx_good_packets` | Штатный агрегат переданных пакетов | TX unicast + multicast + broadcast, собственная 64-битная сумма |
| `rx_bad_packets` | Агрегат, совместимый со штатным web | Формула ниже, не стандартный ifInErrors |
| `tx_bad_packets` | Штатный TxBadPkt | 21; тот же источник, что `tx_excessive_collisions` |
| `rx_unicast_packets` | Принятые unicast-пакеты | 2 |
| `rx_multicast_packets` | Принятые multicast-пакеты | 4 |
| `rx_broadcast_packets` | Принятые broadcast-пакеты | 6 |
| `tx_unicast_packets` | Переданные unicast-пакеты | 10 |
| `tx_multicast_packets` | Переданные multicast-пакеты | 12 |
| `tx_broadcast_packets` | Переданные broadcast-пакеты | 14 |
| `tx_drop_packets` | Штатный счётчик отбрасывания при передаче | 16 |
| `rx_discards` | Обобщённое отбрасывание RX | Всегда `null`: подтверждённого источника/непересекающейся суммы нет |

Фактическая формула `rx_bad_packets` сохраняет необычное поведение штатного UI:

```text
((rx_oversize_packets + tx_oversize_packets) mod 2^32)
+ ((rx_undersize_packets + tx_undersize_packets) mod 2^32)
+ rx_jabbers + rx_fragments + rx_crc_align_errors
```

Она содержит TX-категории. Не переименовывать её в стандартную сумму ошибок
приёма и не складывать с составляющими повторно. Счётчики/агрегаты читаются
последовательно; равенство отдельно полученных сумм не гарантируется.

Адреса чтения этих полей проверены статически. **Приведённые названия и смыслы

Полученный ноль не является отдельным испытанием соответствующего вида ошибок.

| Поле | Предполагаемое значение | Selector |
| --- | --- | --- |
| `rx_bridge_discards` | Отбрасывания на уровне моста | 125 |
| `rx_mac_discards` | Отбрасывания MAC | 84 |
| `rx_undersize_drops` | Отброшенные слишком короткие кадры | 65 |
| `rx_crc_align_errors` | Ошибки CRC/выравнивания | 31 |
| `symbol_errors` | Ошибки символов | 22 |
| `rx_unknown_control_opcodes` | Неизвестные управляющие opcode | 23 |
| `rx_pause_frames` | Принятые pause-кадры | 24 |
| `tx_pause_frames` | Переданные pause-кадры | 25 |
| `drop_events` | События отбрасывания; не обязательно число пакетов | 26 |
| `rx_undersize_packets` | Принятые кадры категории undersize | 35 |
| `tx_undersize_packets` | Переданные кадры категории undersize | 36 |
| `rx_oversize_packets` | Принятые кадры категории oversize | 38 |
| `tx_oversize_packets` | Переданные кадры категории oversize | 39 |
| `rx_fragments` | Фрагменты/ошибочные короткие кадры | 40 |
| `rx_jabbers` | Кадры категории jabber | 43 |

| `tx_multiple_collision_frames` | Кадры с несколькими коллизиями | 18 |

### Распределение по размерам кадров

Это отдельные диапазоны, **не накопительные histogram buckets** Prometheus.
Точные границы с учётом FCS и максимальный размер `max` требуют стендовой проверки.

| RX-поле | TX-поле | Категория размера, байт | Selector RX/TX |
| --- | --- | --- | --- |
| `rx_packets_64` | `tx_packets_64` | 64 | 48 / 49 |
| `rx_packets_65_127` | `tx_packets_65_127` | 65–127 | 51 / 52 |
| `rx_packets_128_255` | `tx_packets_128_255` | 128–255 | 54 / 55 |
| `rx_packets_256_511` | `tx_packets_256_511` | 256–511 | 57 / исключён |
| `rx_packets_512_1023` | `tx_packets_512_1023` | 512–1023 | 60 / 61 |
| `rx_packets_1024_1518` | `tx_packets_1024_1518` | 1024–1518 | 63 / 64 |
| `rx_packets_1519_max` | `tx_packets_1519_max` | 1519–максимум | 66 / 67 |

`tx_packets_256_511` всегда `null`: штатный selector 58 оставляет младшее выходное
слово незаписанным. Новый независимый источник ещё не проверен. Вычислять это поле
вычитанием остальных неодновременных счётчиков нельзя.

## `ports[].poe`

Порты 17–18 имеют `poe: null` целиком: PoE для них не предоставляется этим адаптером.
На 1–16 `enabled: true` и `status: "OFF"` допустимы одновременно: питание разрешено
конфигурацией, но состояние выдачи питания выключено.

| Поле | Тип / единица | Описание |
| --- | --- | --- |
| `enabled` | boolean? | Разрешение PoE по данным штатного кэша |
| `status_code` | integer? | Сырой код текущего состояния, сохраняется и при неизвестной расшифровке |
| `status` | string? | Строка по таблице ниже; неизвестный код → `null` |
| `power_w` | number?, Вт | Мощность, положительное signed16 raw / 10 |
| `current_ma` | number?, мА | Ток, положительное signed16 raw без масштабирования |
| `voltage_v` | number?, В | Напряжение, положительное signed16 raw / 10 |
| `measurements_valid` | boolean? | Сейчас `null`: достоверность и свежесть измерений отдельно не установлены |
| `pd_class` | integer 0–4? | Класс питаемого устройства из известного raw-кода |
| `pd_class_raw` | integer? | Исходный код класса, включая неизвестные значения |
| `priority_code` | integer? | 0 = High, 1 = Middle, 2 = Low; другие коды не расшифровываются |
| `power_limit_mode` | `auto`, `fixed` или null | Raw 330 → auto; другие неотрицательные значения → fixed |
| `power_limit_w` | number?, Вт | Фиксированный лимит raw / 10; при auto — `null` |
| `extend_enabled` | boolean? | Сейчас `null`: источник не реализован |
| `recovery` | object | Конфигурация и сырые счётчики Auto Recovery |

Нулевые и отрицательные **измерения отдельного порта** power/current/voltage
превращаются в `null`, поскольку штатный UI показывает для нуля `---`.
Это правило не распространяется на общий `poe.consumption_w`: там ноль сохраняется.
Мощность, ток и напряжение не вычисляются друг из друга.

| Код статуса | Строка | Значение по штатной таблице |
| --- | --- | --- |
| 0 | `OFF` | Выключено |
| 1 | `TURNING-ON` | Включается |
| 2 | `ON` | Включено |
| 3 | `OVERLOAD` | Перегрузка |
| 4 | `SHORT` | Короткое замыкание |
| 5 | `NOSTANDARD-PD` | Нестандартное питаемое устройство |
| 6 | `VOLTAGE-HIGH` | Высокое напряжение |
| 7 | `VOLTAGE-LOW` | Низкое напряжение |
| 8 | `HARDWARE-FAULT` | Аппаратная неисправность |
| 9 | `OVERTEMPERATURE` | Перегрев |

Расшифровка `pd_class_raw`: **330 → 0, 40 → 1, 70 → 2, 154 → 3, 300 → 4**.
Иные значения дают `pd_class: null`. Например, реальное значение 331 в этом
сеансе сохранено как raw и не объявляется новым классом или неисправностью.
Raw 330 в поле лимита означает Auto, а не фиксированные 33 Вт.

### `ports[].poe.recovery`

| Поле | Тип / единица | Описание |
| --- | --- | --- |

| `startup_delay_seconds` | integer?, с | Настроенная задержка до начала контроля |

| `failures_current` | integer? | Текущее значение счётчика неудач |

| `pings_raw` | integer? | Сырой счётчик проверок из штатной статистики |

Три последних поля читаются как signed16; отрицательные значения дают `null`.
Их переполнение и сброс на железе не испытаны. Наличие настроек не доказывает,
что механизм активен или выполнял перезапуск. Чтение JSON не посылает ping и
не запускает Auto Recovery.

## `loop_prevention`

| Поле | Тип | Описание |
| --- | --- | --- |
| `enabled` | boolean? | Сейчас `null`: активный режим отдельно не установлен |
| `rldp_mask_raw` | uint32? | Текущая программная маска RLDP, RAM `0xbf00e280` |
| `rlpp_mask_raw` | uint32? | Текущая программная маска RLPP, RAM `0xbf00e2a0` |
| `rlpp_self_mask_raw` | uint32? | Программная маска self-loop RLPP, RAM `0xbf00e2a4` |

Нулевая маска не доказывает отсутствия петли при выключенном механизме.
Маски могут включать развёрнутую группу LAG; нельзя без проверки трактовать
каждый бит как подтверждённый заблокированный порт панели. Endpoint только
читает маски, не запускает диагностику петель.

## Обработка при сборе метрик

- Проверять HTTP, JSON, `schema_version` и номера всех 18 портов. При ошибке
  отражать ошибку сбора; не заменять весь ответ нулями.
- `null` пропускать как отсутствующее измерение. Не превращать его в 0 или false.
- Для скорости трафика использовать разность счётчиков и **время на стороне
  сборщика**: бит/с = `8 × Δbytes / Δseconds`. Сырые uptime ticks пока не подходят.
- Уменьшение счётчика может означать сброс или переполнение. Не выводить
  отрицательную скорость; модель переполнения конкретного поля ещё требует проверки.
- Суммы категорий и размерные buckets не являются независимыми величинами;
  избегать двойного учёта и выдачи экспериментальных полей за стандартные IF-MIB.
- Плановый интервал 15 секунд из раннего проекта ещё не проверен длительной
  нагрузкой. Два ручных ответа не доказывают безопасную частоту постоянного опроса.

Готовый Prometheus exporter и Grafana dashboard этим выпуском не добавлены.
Справочник определяет поведение источника, необходимое для их последующей разработки.

## Реальные примеры и воспроизведение проверки

[Первый JSON](evidence/2026-10-17-switchlens/stats-01.json) и
[второй JSON](evidence/2026-10-17-switchlens/stats-02.json) — показания устройства,
опубликованные по запросу владельца. В отличие от `examples/demo.synthetic.json`,
они содержат реальные адреса этого стенда и не предназначены как универсальная
конфигурация. Оригиналы сообщений, скриншоты, SHA-256 и границы проверки —
в [журнале испытания](evidence/2026-10-17-switchlens/README.ru.md).

Из корня репозитория с установленными `requirements-dev.txt`:

```bash
python3 - <<'PY'
import json
from pathlib import Path
from jsonschema import Draft202012Validator
schema = json.loads(Path('schema/stats.schema.json').read_text())
validator = Draft202012Validator(schema)
for path in sorted(Path('docs/evidence/2026-10-17-switchlens').glob('stats-??.json')):
    data = json.loads(path.read_text())
    validator.validate(data)
    assert [p['port'] for p in data['ports']] == list(range(1, 19))
    for port in data['ports']:
        for value in port['counters'].values():
            assert value is None or 0 <= int(value) <= 2**64 - 1
    print(path.name, 'PASS', len(data['ports']), 'ports')
PY
```

Проверка формы и диапазонов не подтверждает точность каждого датчика/счётчика.
Дальнейшие проверки: соответствие штатным страницам, PoE под нагрузкой,
нумерация разъёмов, скорость обновления, сброс/переполнение и длительная работа.

## cooling (v0.1.2)

Необязательный корневой объект новой сборки v0.1.2; в v0.1.1 отсутствует.
Схема остаётся 1, прежние ответы допустимы. Чтение ничего не переключает.
Все integer — JSON-числа; null не означает ноль или исправность.

| Field | Type | Значение |
| --- | --- | --- |
| `speed_mode` | string/null | v0.1.3: общий заданный режим `low`/`fast`; null при неверном state/mux/direction, не измеренные RPM |
| `gpio_control_raw` | uint32? | Сырой mux/control `0xb8003500` |
| `gpio_direction_raw` | uint32? | Направления `0xb8003508`: 0 вход, 1 выход |
| `gpio_data_raw` | uint32? | Данные `0xb800350c`, без интерпретации скорости |
| `controller_state_raw` | uint32? | Слово `0xbf014840`; в тесте упакованная метка, не просто 0/1 |
| `fast_ticks_raw` | uint32? | Быстрый IRQ-счётчик `0xbf002e94`, единица в секундах не проверена |
| `poe_load_raw` | uint32? | Последняя сумма `0xbf014400`, шаг 0,1 Вт; отрицательная сумма даёт null |
| `gpio26_level` | 0/1? | Выборка входного бита, не подтверждённый FAN fault или RPM |
| `gpio27_level` | 0/1? | Уровень выхода; на проверенном устройстве 0 задаёт повышенную скорость обоих вентиляторов, 1 — пониженную; не измеренные RPM и не процент PWM |
| `auto_state` | 0/1? | В авто текущее состояние; в тесте сохранённое; при invalid — null |
| `test_level` | 0/1? | Заданный уровень для test/expired, иначе null |
| `remaining_ticks` | uint32? | Оставшиеся raw-тики; 0 для auto/expired/invalid |
| `test_limit_ticks` | uint32? | 100; это не секунды |
| `mode` | string? | `auto`, `test`, `expired`, `invalid` |
| `fan_rpm` | null | Тахосчётчик и пересчёт не найдены; RPM не измеряются |
| `fan_status` | null | Здоровье отдельных вентиляторов не подтверждено |

`expired` означает: срок истёк, но цикл управления ещё не снял метку теста.
HTTP сам этого не делает. Регистры читаются последовательно, снимок не атомарен;
`poe_load_raw` может отличаться от ранее прочитанного `poe.consumption_raw`.
`auto_state` в тесте не является заново рассчитанным требованием автоматики.
[Команды, упакованное состояние и тайм-аут](COOLING-CONTROL.ru.md).

[Аппаратное наблюдение и ограничения интерпретации](evidence/2026-10-17-cooling/README.ru.md).

В v0.1.3 `mode` — `auto`, `manual` или `invalid`; ручные low/fast без таймера. Прежние `test_level`, `remaining_ticks` и `test_limit_ticks` равны null. Описанные выше значения полей ограниченного теста относятся только к v0.1.2.
