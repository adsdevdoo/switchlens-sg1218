HTTP/JSON: офлайн-прототип на C, 2026-10-16

СТАТУС
Проверено: код собирается и проходит host-тесты; исходники и вывод в этом каталоге.
Это библиотека формирования тела ответа для будущего GET /stats.json. Маршрут
в прошивку ещё не встроен, адаптер живых данных не реализован, прошивочного BIN нет.
Гипотеза: этот код можно перенести в исследованную MIPS-прошивку. Целевая сборка,
ABI, стек, время ответа и поведение ASIC на стенде пока не проверены.

ЧТО РЕАЛИЗОВАНО
Проверено по sg_stats.c / sg_stats.h и tests/test_serializer.py:
- Полная структура schema/stats.schema.json: система, глобальный PoE, 18 портов,
  счётчики, PoE и Auto Recovery по портам, поля диагностики петель.
- Все семь полей экрана System Info присутствуют. name — alias description.
- 128-байтовый буфер вывода; весь JSON в памяти не накапливается. Этот размер
  НЕ является оценкой всего стека: есть кадры вызовов и память адаптеров.
- uint64 выдаётся десятичной строкой без потери точности; мощности/напряжения
  можно передать целыми десятыми, без printf и floating point.
- UTF-8 проверяется, спецсимволы экранируются, строки ограничены в байтах.
  Байтный предел намеренно строже maxLength схемы, считающего символы.
- Ошибка источника и неверный тип/диапазон дают null с отдельным числом ошибок
  в sg_result. Неизвестное значение никогда не подменяется нулём.
- rx_discards и tx_packets_256_511 принудительно null: источник для них даже
  не вызывается. Причины: неизвестная семантика агрегата и дефект selector58.
- Частичные записи повторяются только при положительном прогрессе; 0/ошибка
  немедленно останавливают сериализацию. Последний flush тоже проверяется.

Проверено по sg_mib.c, test_mib.c, tests/test_serializer.py и research/mib-map.json:
- Экспериментальный reader принимает callback read32; прямых MMIO-записей,
  сетевых обращений и исполнения адресов прошивки здесь нет.
- 41 разрешённый односоставной selector, плюс RX/TX двухсловные selector1/9.
  Неизвестные selector, no-op, суммы и дефектный selector58 отвергаются.
- Порты1..16 -> physical0..15; 17/18 -> physical24/25, согласно статическому
  коду file0x4dc3c. Соответствие маркировке панели надо проверить на стенде.
- База регистра = 0x1200 + physical*0x100; offsets сверены с mib-map.json.
- Пара читается high-low-high, максимум3 попытки; при изменении high повтор.
  На ошибке результат вызывающего кода не меняется.
Гипотеза: такой порядок даёт согласованную пару на реальном ASIC. Латчинг,
clear-on-read, реальные разрядности и влияние параллельных читателей не измерены.
41 отдельный счётчик остаётся32-битным; упаковка в uint64 не расширяет железо
и не восстанавливает пропущенные переполнения. Снимок разных регистров не атомарен.

СБОРКА И ПРОВЕРКА НА КОМПЬЮТЕРЕ
Требуются C99-компилятор, make, Python3 и jsonschema. Команды из корня репозитория:
  python3 -m pip install jsonschema
  python3 tools/generate_fields.py
  make test
  ./build/fixture > demo.synthetic.json

fixture — исключительно синтетический источник с тестовыми адресами192.0.2.x.
Ни одной команды к коммутатору эти программы не отправляют.
Данные fixture не означают готовности перечисленных показаний на устройстве.
Все исходники и схема входят в архив; бинарники host-сборки не включены.

Дополнительно проверены AddressSanitizer и UndefinedBehaviorSanitizer:
  ASAN_OPTIONS=detect_leaks=0 make BUILD=build-sanitize \
    CFLAGS='-std=c99 -Wall -Wextra -Werror -O1 -g' \
    SANITIZE='-fsanitize=address,undefined -fno-omit-frame-pointer -fno-pie -no-pie' test
Проверено: среда не поддерживает LeakSanitizer под ptrace; исходный запуск
завершался сообщением "LeakSanitizer does not work under ptrace". Поэтому
отключена только проверка утечек, а ASan/UBSan оставлены. Проверку утечек на
устройстве это не заменяет. В sg_stats.c и sg_mib.c нет динамических аллокаций.
Вывод успешных запусков: docs/host-test-results.txt.

ГРАНИЦЫ АДАПТЕРА
sg_source.begin должен получить небольшой согласованный снимок текущей области;
get выдаёт его поля, has_poe — подтверждённую применимость PoE текущему порту.
Невозможность определить применимость прерывает ответ. Разные порты читаются
последовательно; глобальной атомарности нет. Нельзя отключать прерывания на всё
время HTTP или вызывать обработчики настройки, сброса статистики и защиты петель.
Отдельные MIB-чтения ещё не подключены к sg_source: это следующий слой адаптера.
Строки должны быть ограниченно скопированы из RAM, оставаться валидными до
следующего get, а name и description использовать один снимок исходной строки.

sg_sink.write должен возвращать ПОЛОЖИТЕЛЬНОЕ число принятых байтов, а не status0
штатного emit. Нельзя напрямую присвоить ему адрес штатной функции отправки.
Все callbacks синхронные, с ограниченным временем; рекурсивное использование
общего HTTP-буфера недопустимо. На ошибке прекратить HTTP-ответ; клиент принимает
только полный JSON ожидаемой версии. finish проверяет финальный flush транспорта.
Если HTTP-стек не умеет корректно завершать/обрывать поток, адаптер надо переделать.

ПРИВЯЗКА К ИССЛЕДОВАННОМУ ОБРАЗУ — ПРОВЕРЕНО СТАТИЧЕСКИ
Только SHA256 c9ab17eda7af714f00692d41f440ce84ed0d6c7d678634c364ec1154bb7e3f32.
Перед любыми дальнейшими преобразованиями: python3 tools/audit.py /path/image.bin.
Эта команда проверяет SHA256 и ничего не меняет. Смещения включают update header.
- MIB API VA0xbfc27fb8 ->0xbfc1d930 (file0x15930); helper0xbfc1d7f0 маскирует
  ошибку read. Нельзя считать его возврат доказательством удачного чтения.
  Низкоуровневое чтение VA0xbfc10768/file0x8768 требует отдельной проверки ABI.
- HTTP raw emit VA0xbf01cac0/file0x66f8 возвращает status0/-1; штатные printf
  и end скрывают часть ошибок. Разбор: research/HTTP-JSON-FOLLOWUP.txt.
- SystemInfo: getter пути, RAM и пределы копий — research/SYSTEM-INFO.txt.
- PoE: RAM-кэш, шаг0x30 и масштабы — research/COMPARISON-AND-POE.txt.
- uptime_ticks_raw: RAM0xbf002e90. Параметры таймера найдены; 1 секунда на raw
  tick — гипотеза при LXB200MHz. Частота не подтверждена, uptime_seconds=null.
  Актуальные доказательства: research/PLATFORM-FOLLOWUP.md.
- Диагностика петель: research/MIB-LOOPS-FOLLOWUP.txt. Raw-маски нельзя выдавать
  как подтверждённое состояние блокировки портов.

ЧЕГО ЕЩЁ НЕТ
Данных нет: проверенная MIPS-сборка и linker layout; фактический расход стека/RAM;
проверенный обработчик /stats.json в HTTP-роутере; работающие адаптеры RAM/ASIC;
ограничение времени запроса; подтверждённая периодичность и свежесть PoE-кэша.
При MIPS-сборке uint64 деление может потребовать libgcc; размер runtime надо
учесть, исходя из linker map, а не размера host-объекта.
Наличие полей в JSON не означает наличие источника. Неизвестные поля остаются null.
Не создаются файл на флеше и фоновые записи: предполагается динамический ответ.
Решение об аутентификации существующего HTTP-сервера этим кодом не меняется.
