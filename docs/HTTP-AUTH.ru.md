# HTTP-авторизация и автоматический сбор статистики

Используется вход через форму, сессионная cookie `H_P_SSID` и проверка IP клиента.
Это не HTTP Basic/Digest, Bearer или API-ключ. Вход и сбор должны выполняться
с одного клиентского IP. Перенос cookie браузера на сервер с другим IP сам
по себе не создаёт там действующую сессию.

## Последовательность запросов

Встроенная форма входа по смещению `0x95ecc` отправляет `POST /logon.cgi`.
Поля: `username`, `password`, `logon=Login`, а при обычном входе пустой `cpassword`.
В коде есть выдача `Set-Cookie` с префиксом `H_P_SSID=tplink_`. JavaScript-хеширования
пароля в этой форме не найдено.

Пример для Windows PowerShell (`curl.exe`; подставить свои данные локально):

```powershell
curl.exe -c cookies.txt --data-urlencode "username=ВАШ_ЛОГИН" --data-urlencode "password=ВАШ_ПАРОЛЬ" --data "logon=Login&cpassword=" http://192.168.1.3/logon.cgi
curl.exe -b cookies.txt http://192.168.1.3/stats.json
```

На Linux/macOS команда называется `curl`. Поля запроса прочитаны из прошивки;
полная последовательность команд на устройстве владельца ещё не проверена.
Проверять, что получен JSON ожидаемой схемы с 18 портами: HTML даже с HTTP 200 —
ошибка входа, а не образец метрик. При истечении сессии повторять обычный вход
и обновлять cookie. Длительность сессии здесь не предполагается. Используется
обычный HTTP: пароль/cookie не шифруются при передаче. Реальные пароли и cookie
не публиковать. Сам endpoint статистики только читает.

## Непрерывный сбор

Выполняйте вход и опрос в одном процессе либо на одном хосте с постоянным
исходящим IP. Для каждого свитча храните отдельный файл cookie. Успешный HTTP-код
сам по себе не подтверждает вход: считайте сессию рабочей только после получения
полного и корректного документа метрик из `/stats.json`.

1. Отправьте форму выше методом POST и сохраните cookie ответа. Пароль не нужно
   передавать при каждом запросе статистики: последующие GET используют cookie.
2. Запрашивайте `/stats.json` с этим файлом cookie. Задайте таймаут подключения
   и всего запроса, например 5 и 15 секунд. Это настройки сборщика, а не
   измеренные ограничения прошивки.
3. Разберите весь ответ как JSON и проверьте его по
   [stats.schema.json](../schema/stats.schema.json). Требуются `schema_version: 1`
   и ровно 18 портов с номерами 1–18. HTML входа, обрезанный ответ и произвольный
   JSON-объект не считать образцом метрик.
4. Если вернулась форма входа или отказ авторизации, отбросьте ответ, удалите
   старые cookie, выполните один повторный вход и один повторный GET. Если это
   не помогло, зафиксируйте ошибку сбора и сделайте паузу перед следующей попыткой.
   Не запускайте бесконечный цикл входа. При сетевом таймауте или повреждённом
   JSON фиксируйте ошибку сети/данных, не считайте её автоматически истечением
   авторизации.
5. Начните с одного запроса каждые 30 секунд без параллельных запросов. Это
   осторожный начальный интервал, а не проверенная максимальная частота опроса.
   Используйте сессию, пока свитч её принимает. После перезагрузки, изменения
   IP или отклонения сессии выполните обычный вход заново.

Пример GET после входа с отдельным сохранением заголовков и тела ответа:

```powershell
curl.exe --connect-timeout 5 --max-time 15 -b cookies.txt -c cookies.txt -D stats.headers -o stats.json http://192.168.1.3/stats.json
```

На Linux/macOS замените `curl.exe` на `curl`. `-b` загружает cookie, а `-c`
сохраняет их обновления. Команда только скачивает ответ: сборщик должен отдельно
выполнить проверку и ограниченные повторы, описанные выше. Не публикуйте
`cookies.txt` и `stats.headers`: в них могут находиться сессионные cookie.
Не записывайте тело запроса входа в логи. Храните учётные данные и cookie в файлах,
доступных только учётной записи сборщика. Опрос выполняйте через доверенную сеть
управления: прошивка обслуживает HTTP без шифрования транспорта.

Пусть сессией владеет один сборщик, а панели мониторинга читают уже сохранённые
им метрики. В исследованном коде состояние сессии глобальное; одновременный вход
из браузера или другого сборщика может мешать опросу. Поведение нескольких
клиентов на устройстве пока не проверено.

## Преобразование ответов в метрики

Записывайте время сборщика для каждого принятого ответа. Храните время последнего
успешного сбора и отдельный признак успеха. Ошибка авторизации/сети означает
отсутствие данных, а не нулевой трафик, нулевую мощность PoE или исправный вентилятор.

- Счётчики представлены десятичными строками: используйте Python `int` или
  JavaScript `BigInt`, не преобразование через число с плавающей точкой.
  Скорость рассчитывайте по двум корректным ответам:
  `bits_per_second = 8 * (new_bytes - old_bytes) / elapsed_seconds`.
  Интервал берите по монотонным часам сборщика: масштаб сырых тиков прошивки
  не подтверждён. Если счётчик уменьшился или устройство перезагрузилось,
  пропустите этот интервал и начните отсчёт заново вместо отрицательной скорости.
- Сохраняйте `null` как отсутствие данных, не заменяйте нулём. Обороты и
  индивидуальная исправность вентиляторов пока неизвестны; `cooling.speed_mode`
  показывает заданный общий режим скорости, а не измеренные RPM и не
  подтверждение вращения обоих вентиляторов.
- `system.firmware_version` сохраняет строку версии TP-Link. Заголовок ответа
  `X-SwitchLens-Build` указывает сборку SwitchLens; сохраняйте его рядом с
  образцами, если он присутствует.

Поля формы и проверки сессии установлены по коду прошивки; автоматический цикл
входа, опроса и повторного входа ещё требует проверки на устройстве.

## Исправление сведений о v0.1.3

Владелец подтвердил загрузку v0.1.3 и команды ручного fast/low, но запрос
статистики без входа по-прежнему показывает форму авторизации. Прежнее
утверждение об открытом endpoint было неверным.

Попытка исправления меняла сравнение пути входа в `0x33770` внутри маршрутизатора
`0xbfc3b740`. Но вызывающая функция `0xbfc3ce48` раньше сверяет IP клиента с RAM
`0xbf018df4` и может передать путь `Unauth` вместо запрошенного. Проверка v0.1.3
заходила прямо во внутренний маршрутизатор и пропустила этот внешний барьер.

v0.1.4 полностью удаляет данный хук, функцию, флаг сборки и define. Блок проверки
сессии `0x33740..0x33804` и внешний обработчик `0x34e48..0x34f58` побайтово
совпадают со штатной прошивкой. Новая MIPS-проверка входит через внешний
обработчик: правильная cookie с того же IP пропускается; неверная cookie,
другой IP и отсутствие активной сессии не получают JSON. Это проверка CPU
с синтетическим запросом, а не полный сетевой вход.

v0.1.3 сохранена как история; для штатной авторизации предназначена v0.1.4.
Других попыток обхода авторизации в новую сборку не добавлено.
