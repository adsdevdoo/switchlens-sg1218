Продолжение этапа 1 — HTTP/JSON и PoE, 2026-10-16
Статический анализ; устройство не опрашивалось. Прошиваемого патча нет.
Объект: June BIN SHA256 c9ab17eda7af714f00692d41f440ce84ed0d6c7d678634c364ec1154bb7e3f32.
Файловые смещения включают 16-байтовый заголовок. Доказательства: http-evidence.txt; воспроизведение: python audit_http.py firmware.bin.

1. Проверено: HTTP использует общий выходной буфер [BF010F8C,BF011540), размер 0x5b4=1460 байт. BFC3B278/file33278 сбрасывает указатель и служебные globals. BF01CAC0/file66f8 копирует данные в буфер, при заполнении вызывает BFC38A64 с длиной1460, при ненулевом результате возвращает -1. Успешная обработка возвращает0. Это буферизация тела, не доказательство HTTP Transfer-Encoding: chunked.
Проверено: BFC38A64/file30a64 проверяет объект сокета и protocol6, вызывает BFC37258, сводит его статус к0/-1. Гарантии доставки, ожидание ACK, таймауты и повторный вход требуют дальнейшего анализа/стенда.
Проверено: BF01CBF8/file6830 форматирует в BF011550, сохраняет длину в BF011650 и вызывает raw output. При возврате всегда устанавливает v0=0, теряя ошибку raw output. Форматтер вызывается через BFC339DC/file2b9dc, далее callback@BF00ECCC; отдельного аргумента ёмкости в этом вызове нет. Расстояние до следующего global256 байт — не доказательство объявления массива, но большой вывод одним printf неприемлем.
Проверено: BFC3B2D0/file332d0 отправляет остаток через BFC38A64, но тоже затирает статус нулём.
Проектное решение (гипотеза до испытаний): маленький собственный сериализатор с фиксированным буфером и явной длиной; передавать через raw output с проверкой0/-1. Не использовать штатный printf для полного JSON. Для последнего flush нужен контроль ошибки отдельно. При обрыве прекратить формирование; exporter не должен принимать оборванный документ.

2. Проверено: router BFC3B740/file33740 имеет предшествующую маршрутам проверку строки из request+EC против globalBF001488, управляемую globalBF011660; исключение по строке /logon.cgi@d5924. Отказ ведёт на BFC3CDE8. Это ещё НЕ полный разбор cookie/session и НЕ основание объявлять новый маршрут доступным без входа.
Проектное решение: сохранять существующий путь входа/сессии на первом стендовом варианте. Новый endpoint /stats.json — проект, его нет в штатной прошивке. Согласование простоты/отсутствия дополнительной защиты не требует переписывать весь механизм сессий. Новый TLS/SNMP-сервис не планируется.

3. Проверено: обработчик PoE читает pdclass из uint32@BF01441C + port_index*0x30 (file3ad10..3ad60), powerstatus из uint32@BF014420 + port_index*0x30 (file3ad74..3adc4). Связь имён подтверждают строки pdclass:[@d6e80 и powerstatus:[@d6e8c. Число итераций берётся из BF0143E0.
Проверено ранее: state BF01440A(s16), powerlimit BF01440C(s16), priority BF014410(u32), current BF014416(s16), voltage BF014418(s16), power BF01441A(s16); stride0x30. Масштабы из JS описаны в COMPARISON-AND-POE.txt.
Гипотеза реализации: читать существующий кэш без дополнительных команд PoE-контроллеру. Его свежесть/обновление/согласованность пока не доказаны. enabled и powerstatus должны быть разными полями. pdclass хранится кодом мощности, не номером класса. Нулевое измерение нельзя автоматически считать валидным нулём.

4. Проверено: SignCheck берёт UID в stack+18 через BFC1044C (file45778), длину UID из BF002E80 в stack+500 (457b0..457c8). Далее вызов BF01E1C8 получает a1=stack+18 и a2=эту длину (46064..46088), после финализации20 байт сравниваются с результатом операций над подписью (46138..46198). Инициализирующие слова67452301,EFCDAB89,98BADCFE,10325476,C3D2E1F0 видны в46038..4607c.
Проверено: base64-данные cb400:cb4c8 декодируются в148байт; magic RSA1, поле длины1024, exponent65537. Подпись считывается отдельно из B41FC006 (см. основной отчёт).
Гипотеза высокой уверенности: это RSA/SHA-1 проверка UID флеша, а не хеша всего runtime-образа. В прослеженном вызове хешируется буфер UID. Полный математический аудит реализации RSA и независимые проверки загрузчика НЕ выполнены. Это не разрешение на прошивку и не доказательство отсутствия подписанного boot chain.

5. Данных по-прежнему нет: доказанная единица uptime-тика BF002E90, RX discards, точная аппаратная разрядность и latch MIB, запас стека, полный SPI/bootloader и рабочий recovery. Их не подменяем догадками. По строгим исходным критериям разрешить прошивку пока нельзя.

6. Следующее решение пользователя: переход к этапу2 (стенд). Сначала нужны фото обесточенной платы V5.0 с обеих сторон, читаемые маркировки SoC/flash и предполагаемых UART площадок. По фото выберем напряжения/подключение. Распиновка, уровни и параметры программатора сейчас неизвестны; готовых команд записи/erase не даём. Боевой коммутатор не вскрывать для этого исследования.
