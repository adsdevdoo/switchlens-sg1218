1. ПЛАТФОРМА И КАРТА
Проверено: инструкции MIPS32 big-endian; ext/seb и другие инструкции соответствуют MIPS32r2. Последовательности и абсолютные переходы согласуются с file_offset + 0xbfc08000 для кода во флеш-отображении. Вход после заголовка 0xbfc08010; инициализация @file0x410; переход к main 0xbfc2e760 @file0x6f8.
Проверено: строка @0xd3094 содержит realtek_mcu/CPU_RTL838x_RTL833x/EasySmart_V3/.../dal/maple/dal_maple_l2.c. В образе много dal_maple_*.
Гипотеза: платформа семейства Realtek Maple RTL838x. Точный кристалл/суффикс и физическая маркировка флеша по этому файлу не установлены. Слово 0x8380 @0xf7040 не считать доказательством конкретной модели кристалла.
Проверено: startup @0x620..0x6dc копирует/очищает области:
  file[0x10:0x410] -> 0xbf000000 (векторы);
  file[0x720:0x3160] -> 0xbf000400 (цикл копирует также заключительное слово);
  zero 0xbf002e40..0xbf019528 (включая конечное слово);
  file[0x3160:0x8178] -> 0xbf019528..0xbf01e540.
Проверено: SP устанавливается 0xbf01f800 @0x6e0..0x6f4.
Гипотеза: компактный standalone runtime с циклом событий/таймерными флагами, а не обычный Linux. Основание: main @0x26a44..0x26b74 и прямая инициализация аппаратуры. Название RTOS не установлено. Отсутствие строк Linux/eCos/FreeRTOS само по себе ничего не доказывает.
Проверено: изученные код и веб-ресурсы читаются без распаковки. Отсутствие любых сжатых подблоков не доказано.

2. ЗАГОЛОВОК И ПРОВЕРКИ
Проверено, поля big-endian:
  0x00: d31a20a5 — CRC32.
  0x04: 000f763c — длина файла минус 16.
  0x08: 0dffffff — первое поле-байт проверяется маской 5 в web upgrader; смысл остальных битов неизвестен.
  0x0c: 184d5005 — идентификатор, который сравнивает web upgrader.
Проверено: zlib.crc32(data[0x10:0xf7000]) == 0xd31a20a5. CRC не покрывает весь файл; хвост с параметрами начинается после этого диапазона.
Проверено: web upgrader @0xbfc3dd20 проверяет длину/ID/флаги. @file0x36014..0x36038 вызывает CRC с длиной 0xf6ff0 по адресу staging+0x10 и сравнивает с первым словом staging. CRC-функция RAM VA0xbf01b480 соответствует file0x50b8.
Проверено: SignCheck присутствует, вход VA0xbfc4d718/file0x45718. Вызывает получение UID и чтение 128 байт подписи из отображения 0xb41fc006..0xb41fc086 (функция VA0xbfc5141c/file0x4941c). Есть строка RSA1, операции с большими числами, сообщения Pass/Fail. Инициализация вызывает проверку @file0x26614; её результат влияет на запуск HTTP/TSDP @0x2664c и далее.
Гипотеза: это проверка привязки/подлинности флеша, отдельная от CRC runtime. Полный криптографический поток и входное сообщение пока не доказаны; наличие этих строк НЕ означает автоматически подписанный update, а CRC НЕ исключает проверки загрузчиком.
Данных нет: полный загрузчик, его проверки, поведение восстановления. Сравнение с 20221012/20230220 невозможно без этих файлов.

3. ВЕБ-СТАТИСТИКА И СЧЁТЧИКИ
Проверено: строка /PortStatisticsRpm.htm @0xd5d54. Сравнение маршрута @0x34258..0x34264, переход @0x34280 к handler VA0xbfc4163c/file0x3963c.
Проверено: handler проходит 18 портов. Формат pkts @0xd6c60 = %u,%u,%u,%u,. Четыре функции возвращают 64-битные программные суммы, но в HTML передаются только младшие слова (@0x39894..0x398b8).
  VA0xbfc59870 / file0x51870: сумма selector 2,4,6 (RX unicast/multicast/broadcast).
  VA0xbfc59638 / file0x51638: сумма selector 37,34,43,40,31 (точная семантика компонентов ошибок не установлена).
  VA0xbfc59498 / file0x51498: сумма selector 10,12,14 (TX unicast/multicast/broadcast).
  VA0xbfc59390 / file0x51390: selector21 (используется для TxBadPkt; точная ASIC-семантика ещё требует сверки).
Проверено: общий MIB API VA0xbfc27fb8 — переход к VA0xbfc1d930/file0x15930; параметры по call sites: unit, physical_port, selector, output_pointer. Возврат status; output два 32-битных слова high/low. Это восстановленный ABI, не исходные имена функций.
Проверено: CLI-таблица @0x94170 содержит rx bytes selector0; tx bytes selector8; tx drop packets selector16. CLI выводит только младшее слово через %lx. Для полного 64-битного вывода нельзя копировать этот CLI как есть.
Проверено: jump table @0x93250:
  selector0 -> VA0xbfc1d9e8: читает RX high затем low, выдаёт только low.
  selector1 -> VA0xbfc1da00: читает RX low затем high, выдаёт оба слова.
  selector8 -> VA0xbfc1da30: читает TX high затем low, выдаёт только low.
  selector9 -> VA0xbfc1da48: читает TX low затем high, выдаёт оба слова.
  selector16 -> VA0xbfc1da8c: TX drop, 32-bit с нулём в high.
Проверено: адрес блока задаётся 0x1200 + (physical_port << 8).
  RX high +0x00, low +0x04;
  TX high +0x08, low +0x0c;
  TX drop +0x2c.
Проверено: низкоуровневая ветка VA0xbfc10768/file0x8768 читает MMIO (0xbb000000 | register_offset), если callback не установлен; иначе вызывает callback. Для unit0 отсутствие callback на конкретном стенде ещё нужно проверить.
Гипотеза: selectors1/9 — правильные источники rx_bytes/tx_bytes. Код поддерживает два слова, но фактическая разрядность ASIC и консистентность пары при переносе low требуют теста; считать 64 аппаратных значащих бита доказанными нельзя.
Проверено: mapping VA0xbfc55c3c/file0x4dc3c преобразует логические индексы16/17 в ASIC24/25; 0..15 остаются прежними. Физические подписи на панели и LAG-семантику необходимо сверить на стенде. Существующие web wrappers могут суммировать члены группы — для per-port JSON нельзя бездумно использовать такую агрегацию.
Данных нет: надёжная привязка RX discards и полное соответствие TX drop определению ifOutDiscards. В JSON пока называть tx_drop_packets, а не выдавать это за IF-MIB.

4. HTTP, UDP, ТАЙМЕРЫ
Проверено: существующий форматированный вывод HTTP VA0xbf01cbf8/file0x6830; использует общий буфер 0xbf011550 и функцию форматирования VA0xbfc339dc, затем raw output VA0xbf01cac0. По соседним globals нельзя предполагать неограниченную длину строки; большой JSON одним вызовом опасен без определения размера буфера.
Гипотеза: выводить JSON короткими фрагментами на порт через существующий HTTP-механизм. Нужно отдельно проверить частичные отправки и блокировки. Не нужен новый поток или запись статистики во флеш.
Проверено: инициализация TSDP file0x3fcf0 создаёт объект с protocol17 через VA0xbfc38780, регистрирует callback0xbfc48db0 и bind VA0xbfc38b3c на29808. Отправка на29809 @0x40828..0x40844 вызывает VA0xbf01ca4c/file0x6684. Wrapper проверяет protocol17 и передаёт данные VA0xbf01c7d4. ABI и низший сетевой тракт не полностью описаны; для JSON это не основной путь.
Проверено: ISR VA0xbf01a094/file0x3ccc увеличивает uint32@0xbf002e94 каждый тик; каждые20 тиков увеличивает uint32@0xbf002e90. Main опрашивает таймерные флаги через VA0xbfc10480 и очищает через0xbfc10498, вызывает event dispatcher0xbfc2df8c.
Гипотеза: @0xbf002e90 можно использовать как основу uptime. Единица времени ещё не доказана; до калибровки выводить сырые тики с явным названием, не uptime_seconds. API создания RTOS-задач не найден.

Гипотеза: это подходящая область для небольшого кода и констант, исполняемых из флеш-отображения. Её резервирование/допустимость записи пока не доказаны.

Гипотеза: отдельный read-only /stats.json либо расширение handler статистики. Выбор после анализа router/auth и ограничений HTTP output.
Поля v1: schema_version, port, link, speed_mbps, rx_bytes/tx_bytes строками, tx_drop_packets, существующие packet counters. Uptime в секундах только после калибровки. RX discards отсутствует/null до идентификации; никаких фиктивных нулей.
Для локалки можно отдельный маршрут чтения без сессии; это потребует ограниченного изменения маршрутизации, не глобального отключения auth.
